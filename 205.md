Starting with layer 1, the scheduler and block manager. I'm reading the C++ first.

Pinning is how forked and prefix-shared sequences share a block without copying it. Next is the top of `_schedule()`: whether this step runs prefill or decode.

Preempted sequences end in one of two ways. By default they are reset and put at the front of `waiting` to be recomputed, and a later prefill may recover much of the work from the prefix cache. With `stop_preempted_request` they finish as `FINISHED_PREEMPTED` instead. Structured-output requests are always stopped, because grammar state can't be recomputed. A `COMPLETION` (decode-only) engine must use stop mode, since it has no prefill channel.

After picking the survivors, decode calls `_mtp_varlen.schedule(...)`. That is where DSpark's per-sequence draft lengths get set, so it connects to the earlier speculative-decoding diagram.

Layer 1 recap: the block manager hands out ref-counted blocks, and the scheduler alternates prefill (budgeted and chunked) with decode (one slot per sequence, evicting the longest-running first when blocks run out).

Prompts shorter than one 128-token unit store nothing. Chunked prefill stores only on its last chunk. During decode, a replica region copies the window each time a sequence crosses a 128 boundary, so the final store has a clean point to read from.

**Ops, in code:**
- `store_kv_cache(kv, kv_cache, slot_mapping)` quantizes bf16 KV and writes it to its paged slots. A slot of -1 means padding.
- `load_paged_kv_cache(...)` reads compact block ranges back for prefix hits.
- `select_state_slice` and `load_state_to_cache` gather the window out of the circular SWA buffer for storing, and write it back into a slot on load.

Layer 3. Reading the graph runner and how `ModelRunner` uses it.

The captured sizes aren't every integer. With the default interval of 8 and a max of 64, they are `1, 2, 4, 8, 16, 24, …, 56, 64`. A batch of 21 tokens is padded up to 24:

Here is how "Pick total_q" works in `mtp_varlen.hpp`:

1. Start with one token per sequence, and track the expected number of accepted tokens.
2. Sort every draft token by its confidence-head accept rate, highest first, and add them one at a time.
3. After each addition, estimate step time as `curve_ms(graph size) + slope × size + sampler_ms`, and compute expected tokens per ms.
4. Keep the batch size with the best ratio. Because graph sizes are discrete, adding a token that doesn't cross into the next graph is nearly free, and that is why the curve matters.
5. Give each chosen draft token's sequence one more `seqlen_q`.

The sizing uses accept rates from two rounds ago and the per-sequence allocation uses last round's, because ZOS delays the newest confidence values by a step.

The startup profile takes 1 warmup replay and 5 timed replays per size, drops the high and low, and averages across the expert-parallel group. It's cached on disk with a 1-hour TTL, keyed by model, parallel config, and sizes. `update_runtime` then adjusts the forward-time slope from live timings.
