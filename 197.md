Good question — this is a classic "uniqueness constraint that spans a join" problem. Both of the approaches you mentioned have real weaknesses, so let me walk through what's actually available, since the right choice depends on whether you can tolerate a race condition and how many tables are involved.

**Problem with the EXISTS-check approach**

```sql
SELECT 1 FROM A WHERE A.a = ? 
  AND EXISTS (SELECT 1 FROM B WHERE B.b = ?)
```

This is a check-then-act pattern. Under `READ COMMITTED` (Postgres default), two concurrent transactions can both pass the check before either commits its insert — you get a TOCTOU race and end up with duplicates anyway. It only "works" if you also serialize writers somehow (see below).

**Problem with the JSON-hash approach**

Storing composed JSON + hashing it has two issues:
1. **Postgres hash indexes can't back a UNIQUE constraint** — only btree access methods can enforce uniqueness in Postgres. So "hash index" in the literal Postgres sense won't give you the constraint you want.
2. JSON serialization isn't canonical — key order, whitespace, or numeric formatting differences (`{"a":1,"b":2}` vs `{"b":2,"a":1}`) produce different hashes for logically identical data, silently defeating the uniqueness check.

Here's what people actually use in practice, roughly in order of how much you should prefer them:

**1. Denormalize the key columns (not JSON) + composite UNIQUE / generated column**

If the "cross-table" values are effectively foreign keys or copyable scalars, pull them into the row that needs uniqueness enforced:

```sql
ALTER TABLE C ADD COLUMN a_key text, ADD COLUMN b_key text;
ALTER TABLE C ADD CONSTRAINT uq_c_composite UNIQUE (a_key, b_key);
```

Or, if the values are derivable from a JSONB payload already in the row, use a `GENERATED ALWAYS AS ... STORED` column instead of a blob:

```sql
ALTER TABLE C ADD COLUMN composite_key text
  GENERATED ALWAYS AS (payload->>'a' || ':' || payload->>'b') STORED;
CREATE UNIQUE INDEX uq_c_composite_key ON C (composite_key);
```

This is atomic, race-free (the constraint is enforced by the same row's insert), and fully queryable/debuggable. This is the closest "upgrade" of your JSON idea — same principle, but as real columns instead of an opaque blob, so btree can actually enforce it.

**2. Uniqueness ledger / registry table (the standard pattern for true cross-table keys)**

When the uniqueness genuinely depends on rows living in *different* tables that aren't naturally denormalizable into one row, create a small dedicated table whose PK/unique index *is* the composite business key, and insert into it in the same transaction as your real writes:

```sql
CREATE TABLE uniq_registry (
  business_key text PRIMARY KEY  -- e.g. 'A:123|B:456'
);

BEGIN;
INSERT INTO uniq_registry (business_key) VALUES ('A:123|B:456'); -- fails fast if duplicate
INSERT INTO A (...) VALUES (...);
INSERT INTO B (...) VALUES (...);
COMMIT;
```

This is race-free by construction — the PK violation on `uniq_registry` naturally serializes concurrent conflicting transactions, and you don't need SERIALIZABLE isolation for it. This is the pattern used a lot in sharded/distributed systems (and CDC-heavy systems like the ones you work with) precisely because it doesn't depend on cross-table locking.

**3. Hash column, done correctly**

If the composite key is large or built from many fields, hash it — but store the hash as a fixed-length column with a **btree unique index**, using a canonical (sorted, delimiter-based, not JSON) serialization before hashing:

```sql
ALTER TABLE C ADD COLUMN key_hash bytea
  GENERATED ALWAYS AS (digest(a_val || '\x00' || b_val, 'sha256')) STORED;
CREATE UNIQUE INDEX uq_c_key_hash ON C (key_hash);
```

This is fine for avoiding wide composite indexes, but don't use it just to avoid designing the canonical key — canonicalization is still required, and collisions (SHA-256, negligible but nonzero) should be something you've consciously accepted.

**4. Application-level serialization when denormalization isn't possible**

If you truly can't restructure schema (e.g. legacy tables you don't own), fall back to:
- `pg_advisory_xact_lock(hashtext(key))` before the EXISTS check + insert, to serialize writers for the same key, or
- `SERIALIZABLE` isolation with retry-on-`40001` logic.

Both work but add latency/retry complexity that patterns 1–2 avoid entirely.

**My recommendation**: for your case, prefer #2 (registry table) if the tables genuinely can't be merged, or #1 (generated column + composite unique index) if the data can live in one row. Avoid the JSON+hash-index idea as originally framed — keep it, but as a canonicalized column with a real btree unique index, not a hash index type.


At a million-plus rows, doing live multi-row EAV matching (`EXISTS` per key, repeated per check) becomes both slow and still race-prone. The fix is to stop checking B live and instead **maintain a rollup that summarizes B's rows per entity**, updated incrementally via trigger — so each check touches O(1) rows, not O(n).

**Why the naive EAV check breaks down at scale**

```sql
-- "entity must have exactly {k1:v1, k2:v2, k3:v3}"
SELECT id FROM B WHERE id = ? AND key = 'k1' AND value = 'v1'
INTERSECT
SELECT id FROM B WHERE id = ? AND key = 'k2' AND value = 'v2'
INTERSECT
SELECT id FROM B WHERE id = ? AND key = 'k3' AND value = 'v3'
```

Each added key-value pair is another self-join or `INTERSECT`/`EXISTS` against a 1M+ row table. Even with a good index on `(id, key, value)`, this is still checked at query time on every write, and it's still check-then-act — a race is still possible unless you serialize.

**The fix: maintain a per-entity rollup, updated incrementally**

The trick is that B's rows don't all need scanning every time — only the rows belonging to *that one entity* change on any given write. So maintain a small summary table, one row per entity, that's kept current via trigger:

```sql
CREATE TABLE b_rollup (
  id          bigint PRIMARY KEY,
  composite   text,     -- canonical form, e.g. 'k1=v1|k2=v2|k3=v3'
  key_hash    bytea GENERATED ALWAYS AS (digest(composite, 'sha256')) STORED
);
CREATE UNIQUE INDEX uq_b_rollup_hash ON b_rollup (key_hash);
```

Trigger on B recomputes just that entity's row whenever it changes:

```sql
CREATE OR REPLACE FUNCTION refresh_b_rollup() RETURNS trigger AS $$
DECLARE
  target_id bigint := COALESCE(NEW.id, OLD.id);
  composite_val text;
BEGIN
  SELECT string_agg(key || '=' || value, '|' ORDER BY key)
    INTO composite_val
    FROM B
    WHERE id = target_id;

  INSERT INTO b_rollup (id, composite)
    VALUES (target_id, composite_val)
  ON CONFLICT (id) DO UPDATE SET composite = EXCLUDED.composite;

  RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_b_rollup
AFTER INSERT OR UPDATE OR DELETE ON B
FOR EACH ROW EXECUTE FUNCTION refresh_b_rollup();
```

This scales fine at any table size because:
- The `SELECT ... WHERE id = target_id` hits an index on `B(id, key)` and only reads that entity's handful of rows — cost doesn't grow with total row count in B.
- `ORDER BY key` gives you canonical ordering, so logically-identical key sets always hash the same way (unlike raw JSON serialization).
- The uniqueness constraint lives on `b_rollup.key_hash`, enforced by a real btree unique index — no EAV joins at check time at all.

**On the race condition**

The `ON CONFLICT (id) DO UPDATE` handles concurrent writes *to the same entity's* rollup safely. But if two different entities could end up computing the *same* composite key concurrently (i.e., the actual uniqueness violation you're trying to catch), that's caught by `uq_b_rollup_hash` — the second transaction's rollup upsert will raise a unique violation naturally, since Postgres enforces that constraint transactionally regardless of trigger timing.

**If it's a subset match rather than exact match** ("must contain at least these key-values, may have others"), the rollup approach doesn't directly apply — that's a different semantic (existence of a covering set, not equality of a set), and usually needs either a GIN index on an array/jsonb aggregate with `@>` containment, or is better modeled by pulling those specific required keys out as real columns (pattern #1 from before) since "the entity must always have this attribute" tends to mean it's not really open-ended EAV data.

```sql
                  coalesce(frag_a,'') || '||' ||
                  coalesce(frag_b,'') || '||' ||

);

```

```sql

BEGIN
  INSERT INTO entity_signature (id, frag_a)
    VALUES (COALESCE(NEW.id, OLD.id), NEW.a_val)
  ON CONFLICT (id) DO UPDATE SET frag_a = EXCLUDED.frag_a;
  RETURN NULL;
END;
$$ LANGUAGE plpgsql;

-- Table B contributes the EAV rollup from before
CREATE OR REPLACE FUNCTION refresh_frag_b() RETURNS trigger AS $$
DECLARE target_id bigint := COALESCE(NEW.id, OLD.id);
DECLARE frag text;
BEGIN
  SELECT string_agg(key || '=' || value, '|' ORDER BY key)
    INTO frag FROM B WHERE id = target_id;

  INSERT INTO entity_signature (id, frag_b)
    VALUES (target_id, frag)
  ON CONFLICT (id) DO UPDATE SET frag_b = EXCLUDED.frag_b;
  RETURN NULL;
END;
$$ LANGUAGE plpgsql;
```

Why per-source columns instead of one shared "recompute everything" function:
- **Isolation** — a write to B never has to re-read A or C. Cost per write stays proportional to that one source, not the whole entity across every table.
- **Ordering safety** — fragments are positional columns, not concatenated in whatever order triggers happen to fire. No canonical-ordering bugs from race conditions between two tables' triggers.
- **Debuggability** — if uniqueness breaks, you can see exactly which fragment changed and diff it, instead of reverse-engineering one opaque blob.

Add more sources later by adding a column + one trigger — no changes to existing sources' triggers.

**Case 2: source tables don't share a common id — you need a join to relate them**

This happens when, say, A.a_id → B.a_id but C relates via a different foreign key, or the "entity" is really a *relationship* between rows in different tables rather than a single id. Here the composite key isn't "properties of one entity" — it's "the tuple of join keys that identifies a business relationship." Two sub-cases:

- **If the join path is stable and known upfront** (e.g. always A ⋈ B ⋈ C on fixed columns), don't try to build a rollup per raw table at all — instead define a **junction/relationship table** whose row *is* the business relationship, with the composite key made of the actual foreign key values, and trigger off *that* table instead of the source tables individually:

```sql
CREATE TABLE relationship_key (
  a_id bigint, b_id bigint, c_id bigint,
  composite text GENERATED ALWAYS AS (a_id::text || '|' || b_id::text || '|' || c_id::text) STORED,
  PRIMARY KEY (a_id, b_id, c_id)
);
```
No hashing needed here at all — a composite PK on the actual key columns is simpler and just as fast, since you're not folding in EAV-style variable data.

- **If the join path itself is dynamic** (which table relates to which depends on data), that's usually a sign the uniqueness rule needs to be enforced in application code with an advisory lock keyed on the resolved relationship, rather than purely in schema — because Postgres constraints can't express "uniqueness over a dynamically-determined join."

Here's the full design, summarized:

**The problem**
Enforce a uniqueness constraint on a business key composed from data spread across up to ~10 tables (all sharing one master id), including an EAV-style table (id, key, value) that can contribute multiple rows — at 1M+ row scale.

**Why the naive approaches fail**
- `EXISTS`-chain checks at write time: check-then-act race condition, and cost grows with table size since it re-scans on every write.

**The solution: incremental rollup + real unique constraint**

1. **One `entity_signature` table**, keyed by the shared master id, with one fragment column per source table:
```sql

  id        bigint PRIMARY KEY REFERENCES master(id),
  frag_a    text,
  frag_b    text,   -- EAV rollup, e.g. 'k1=v1|k2=v2' (sorted by key)
  frag_c    text,
  composite text GENERATED ALWAYS AS (
              coalesce(frag_a,'§') || '#' ||
              coalesce(frag_b,'§') || '#' ||
              coalesce(frag_c,'§')
            ) STORED,

);
CREATE UNIQUE INDEX uq_entity_sig_hash ON entity_signature (key_hash);
```

2. **One AFTER trigger per source table**, each only touching its own fragment column via `INSERT ... ON CONFLICT (id) DO UPDATE`. For the EAV table, the trigger recomputes just that entity's key-value rows (indexed lookup, not a full-table scan), sorted by key for a canonical order.

3. **Race safety** comes from the real btree `UNIQUE INDEX` on `key_hash` — Postgres enforces it transactionally regardless of trigger timing, so no advisory locks or `SERIALIZABLE` isolation needed.

4. **Design details that matter**: sentinel value for NULL fragments (not empty string), delimiter between fragments (not just within them), sorted key-value pairs for the EAV fragment — all to avoid accidental collisions between different data combinations.

5. **Cost stays flat as data grows**: each trigger only reads/writes rows for its one entity, never scans other tables, so performance doesn't degrade as the 1M+ row tables grow further.

6. **Scaling the table count**: fine as fixed columns under ~10 sources; adding one is just a new column + trigger. If it ever grew past ~10-15 or became dynamic, you'd switch to a `(id, source_name, fragment)` fragment table instead.

7. **Backfill**: populate `entity_signature` from existing data in batches before turning the triggers on for new writes.

Good instinct — you want a friendly "this already exists" check rather than parsing a raw unique-violation exception. Here's how to do it safely, since a naive pre-check on its own reintroduces the race condition we've been avoiding.

**Why a bare pre-check isn't enough on its own**

```sql
-- transaction 1                          -- transaction 2
SELECT 1 FROM entity_signature            SELECT 1 FROM entity_signature
  WHERE key_hash = ?;  -- not found         WHERE key_hash = ?;  -- not found
-- proceeds to insert...                  -- proceeds to insert...
```

Both transactions can pass the check before either commits — you're back to TOCTOU. So the UK constraint has to stay as the ultimate backstop regardless. What changes is *how* you turn a would-be violation into a clean, early, human-readable rejection instead of a raw constraint-violation error bubbling up.

**Pattern: advisory lock scoped to the hash, then pre-check, then write — all in one transaction**

```sql
CREATE OR REPLACE FUNCTION upsert_entity_signature(
  p_id bigint,
  p_frag_a text,
  p_frag_b text,
  p_frag_c text
) RETURNS void AS $$
DECLARE
  v_composite text;
  v_hash bytea;
  v_existing_id bigint;
BEGIN
  v_composite := coalesce(p_frag_a,'§') || '#' ||
                 coalesce(p_frag_b,'§') || '#' ||
                 coalesce(p_frag_c,'§');
  v_hash := digest(v_composite, 'sha256');

  -- Serialize any concurrent writers targeting the SAME composite key.
  -- Different keys use different lock ids and don't block each other.
  PERFORM pg_advisory_xact_lock(hashtext(encode(v_hash, 'hex')));

  -- Now the check is race-free: no other transaction can be mid-write
  -- on this same key while we hold the lock.
  SELECT id INTO v_existing_id
    FROM entity_signature
    WHERE key_hash = v_hash AND id != p_id;

  IF v_existing_id IS NOT NULL THEN
    RAISE EXCEPTION 'DUPLICATE_BUSINESS_KEY: entity % already has this composite key (held by id %)',
      p_id, v_existing_id
      USING ERRCODE = 'P0001';
  END IF;

  INSERT INTO entity_signature (id, frag_a, frag_b, frag_c)
    VALUES (p_id, p_frag_a, p_frag_b, p_frag_c)
  ON CONFLICT (id) DO UPDATE
    SET frag_a = EXCLUDED.frag_a, frag_b = EXCLUDED.frag_b, frag_c = EXCLUDED.frag_c;
END;
$$ LANGUAGE plpgsql;
```

Why this works:
- `pg_advisory_xact_lock` is held only for the current transaction and released automatically at commit/rollback — no manual unlock needed, no orphaned locks if the app crashes.
- Locking is scoped **per key**, not global — two different composite keys never contend with each other, so this doesn't become a bottleneck as write volume grows.
- Because the lock is acquired *before* the `SELECT`, no other transaction can slip an insert in between your check and your write. The race window is closed, not just narrowed.
- The `RAISE EXCEPTION ... USING ERRCODE` gives you a distinguishable, custom error your application layer can catch by code/message rather than parsing a generic `23505` unique-violation — cleaner separation between "expected business rule violation" and "unexpected DB error."

**Calling it from your application layer**

```sql
BEGIN;
SELECT upsert_entity_signature(123, 'a-val', 'k1=v1|k2=v2', 'c-val');
COMMIT;
```

Catch the `P0001` (or whatever custom SQLSTATE you assign) specifically, and surface it as a normal validation error to the caller — same shape as any other business-rule rejection, not an unhandled DB exception.

**If you want an even earlier, non-transactional check** (e.g. for UI validation before the user even submits), you can expose a read-only version of just the `SELECT` — but treat that purely as a UX nicety, not a correctness guarantee. The advisory-lock version above must still run at actual write time regardless, since only that one is race-free.

One thing worth deciding: do you want the duplicate check to be "reject outright" (fail the whole write), or "reject and return the existing id so the caller can decide to update instead"? The function above does the former — happy to adjust if you want an upsert-or-tell-me-who-owns-it behavior instead.



Moving the check "up" to the application layer is reasonable for UX and business-logic clarity, but there's an important limit to be upfront about: **if you have more than one application instance (or even one instance with concurrent request handling), the application layer alone cannot be race-free without some external coordination.** The DB constraint isn't just bureaucracy — it's the one component that's naturally single-threaded per row at the storage engine level. So the real question is *how much* of the responsibility can move up, and what coordination you swap in to replace what Postgres was doing for you.

Here are the levels, from safest to riskiest:

**Level 1 — App does the pre-check + friendly rejection; DB constraint stays as the actual enforcement (recommended)**

This is "shift left" validation: the app calls a read (or a stored proc, or a lightweight `SELECT EXISTS`) before attempting the write, and handles a clean rejection path. The DB unique constraint remains the correctness backstop, but 99%+ of real-world duplicate attempts (a user resubmitting a form, retried API calls) get caught early and cheaply, with a normal-looking business error instead of a DB exception.

```
app: check() -> not found -> proceed to write
db:  INSERT ... ON CONFLICT DO NOTHING / RAISING
app: if DB rejects anyway (rare race), catch that specific error and
     surface the same "duplicate" message as the pre-check would have
```

This is not "instead of" the DB — it's "in front of" the DB. You get app-layer control over messaging/logic, while Postgres remains the source of truth for correctness. Most systems that say "we handle uniqueness in the app" actually mean this.

**Level 2 — Distributed lock coordinating multiple app instances**

If you genuinely want the *serialization* itself (not just the pre-check) to live outside Postgres — e.g. because you're moving toward sharding, or want the lock visible/manageable independent of DB sessions — use a distributed lock service:

- **Redis** (`SET key NX PX ttl`) — simplest, most common; the app acquires a lock keyed by the composite hash before checking + writing, releases after.
- **etcd / ZooKeeper** — stronger consistency guarantees, more operational overhead; overkill unless you already run one for other coordination.

```
lock := redis.SetNX("lock:" + hash, ttl=5s)
if !lock { return DuplicateError }
defer redis.Del("lock:" + hash)

exists := app_check(hash)
if exists { return DuplicateError }
write_to_db()
```

Caveats you inherit by taking this on yourself: TTL tuning (lock expiring mid-transaction vs. held forever on crash), Redis becoming a new single point of failure for correctness, and needing `SETNX`+TTL to be atomic (it is, in modern Redis) to avoid a second TOCTOU gap in the locking mechanism itself.

**Level 3 — Single-writer-per-key pattern (no external lock service needed)**

Given your background with RabbitMQ/AMQP — this is often the cleanest fit for your stack. Route writes for a given composite key to a single consumer via consistent hashing on the queue/partition key (like Kafka partition keys or a hash-routed AMQP consumer). Only one consumer ever processes a given key at a time, so the "check + write" sequence is naturally serialized without any lock at all — the ordering guarantee comes from the message routing, not from the DB or a lock service.

```
producer -> routes message by hash(composite_key) -> partition N
consumer N processes messages for that partition serially
  -> in-memory or local check -> write -> ack
```

This is a strong fit if you're already doing CDC/event-driven work — you get the serialization "for free" from the messaging topology rather than bolting on Redis.

**What I'd actually recommend for your case**

Given you're at 1M+ rows across ~10 tables with a shared master id, and presumably a normal request/response API (not purely event-driven) — **Level 1 is almost certainly the right target.** Full removal of DB-layer enforcement (Level 2/3) only pays off if you're already committed to a distributed-lock or single-writer architecture for other reasons; adopting it *purely* to move a uniqueness check out of Postgres usually adds more operational risk than it removes.

This is a legitimate optimization — but it can only ever be a **fast-path pre-check**, never the enforcement mechanism, for the same TOCTOU reason as before.

**Two very different things people mean by "keep it in memory" — pick one deliberately**

**A. Local cache, single instance, advisory only**
```
in-memory Set<hash> loaded at startup from entity_signature.key_hash
on write attempt:
  if hash in local_set -> reject early, no DB round trip
  else -> proceed to DB (advisory lock + check + insert, as before)
          on success -> add hash to local_set
```
This is safe as an optimization because the DB layer is still the actual gate — the in-memory set only ever produces false negatives (misses, sent through to DB) never false positives that bypass the DB check. Worst case if the cache is stale: an extra unnecessary DB round-trip, not a correctness bug.

**B. Shared in-memory store across instances (e.g. Redis set, not local heap)**
If you're multi-instance, a *local* heap-based set is useless for coordination — each instance has its own copy and won't see writes from other instances. If you want the "in memory" speed benefit *and* multi-instance visibility, that's actually Redis (Level 2 from before) doing double duty as both cache and lock — same tool, two purposes.

**What must NOT go purely in memory**

- The **hash set itself must be rebuildable from Postgres at any time** — treat it as a cache, not a store. If a process restarts and loses local memory, it should reload from `entity_signature`, not treat an empty cache as "nothing exists yet."
- **Never skip the DB-side unique index because the in-memory check passed.** The in-memory check reduces load; it doesn't replace the constraint. Two concurrent requests can still both miss in different instances' local caches and both reach the DB — the unique index is what stops the second one from committing.

**Practical recommendation given your setup**

Since you're already running `entity_signature` with a real unique index as the backstop:
- If single app instance (or instance-local concurrency only): local in-memory `HashSet<bytea>` populated at startup + updated on successful writes is a fine, low-risk speedup.
- If multi-instance: don't bother with local memory — just query Postgres directly for the pre-check (it's an indexed point lookup on `key_hash`, which is fast — sub-millisecond on a btree lookup even at 1M+ rows) unless you have concrete evidence that DB round-trip latency is actually your bottleneck. Premature caching here adds a consistency problem in exchange for optimizing a query that's probably already fast.

Is Postgres round-trip latency actually a measured problem for you, or is this more about wanting the check to conceptually "live" in the app layer? That changes whether in-memory caching is solving a real performance issue or adding complexity for a check that's already cheap.



Compute the hash in the DB, not the app — and get it back via `RETURNING` on the success path. Here's why, and how it fits your flow.

**Why DB-side, not app-side**

The composite key depends on `frag_b`, which is itself an aggregation across possibly-multiple rows in the EAV table B (`string_agg(key||'='||value, '|' ORDER BY key)`). If the app also needs to replicate that aggregation + sort + delimiter logic in its own language just to compute a hash, you now have **two implementations of canonicalization that can drift** — a schema change, a delimiter tweak, a sort-order fix, anything, and now app and DB disagree about what "the same key" means. That's a much worse bug than an extra round-trip, because it fails silently (two different-looking apps' hashes both "work" individually, but never match each other).

Keep canonicalization as **one function, one place** — the generated columns in Postgres already are that place.

**How the app gets the hash on the success path**

Use `RETURNING key_hash` on the write, so the app never computes it — it only ever *receives* it from the DB after a real write succeeded:

```sql
CREATE OR REPLACE FUNCTION upsert_entity_signature(
  p_id bigint,
  p_frag_a text,
  p_frag_c text
) RETURNS bytea AS $$
DECLARE
  v_composite text;
  v_hash bytea;
  v_existing_id bigint;
  v_frag_b text;
BEGIN
  -- frag_b is derived from B directly, not passed in by the app,
  -- since the app doesn't own B's aggregation logic
  SELECT string_agg(key || '=' || value, '|' ORDER BY key)
    INTO v_frag_b FROM B WHERE id = p_id;

  v_composite := coalesce(p_frag_a,'§') || '#' ||
                 coalesce(v_frag_b,'§') || '#' ||
                 coalesce(p_frag_c,'§');
  v_hash := digest(v_composite, 'sha256');

  PERFORM pg_advisory_xact_lock(hashtext(encode(v_hash, 'hex')));

  SELECT id INTO v_existing_id
    FROM entity_signature
    WHERE key_hash = v_hash AND id != p_id;

  IF v_existing_id IS NOT NULL THEN
    RAISE EXCEPTION 'DUPLICATE_BUSINESS_KEY: entity % conflicts with id %', p_id, v_existing_id
      USING ERRCODE = 'P0001';
  END IF;

  INSERT INTO entity_signature (id, frag_a, frag_b, frag_c)
    VALUES (p_id, p_frag_a, v_frag_b, p_frag_c)
  ON CONFLICT (id) DO UPDATE
    SET frag_a = EXCLUDED.frag_a, frag_b = EXCLUDED.frag_b, frag_c = EXCLUDED.frag_c;

  RETURN v_hash;  -- only reached on success
END;
$$ LANGUAGE plpgsql;
```

Application side:

```python
try:
    row = db.execute("SELECT upsert_entity_signature(%s, %s, %s)", (id, frag_a, frag_c))
    returned_hash = row[0]
    local_set.add(returned_hash)   # only added on success, as you said
except DuplicateBusinessKey as e:
    return reject_to_caller(e)
```

**What this gives you**

- The app never needs to know the hash algorithm, delimiter, sentinel, or sort rule — it just passes raw fragment values it *does* own (like `frag_a`, `frag_c`) and lets the function assemble/hash the rest.
- `local_set` is populated exclusively from confirmed successful writes — never from a guess or a pre-computed value the app derived itself — so it can't drift from what Postgres actually persisted.
- If canonicalization logic changes later (new delimiter, new source table, whatever), you change it in exactly one function — the app code doesn't need to know or care.

One open point: does your app ever need to do the pre-check *before* calling this function (e.g. to show a "this already exists" message without attempting a write at all), or is attempt-and-catch-the-exception an acceptable UX for you? If you want the former, you'd want a separate read-only `compute_signature_hash(p_id, p_frag_a, p_frag_c) RETURNS bytea` function (same canonicalization, no lock/write) that the app can call just to look up `local_set`/`entity_signature` without touching data.


Good catch — yes, you do want it on the fail path too, and the current design (raising an exception) actually makes that awkward, since a `RAISE EXCEPTION` aborts the function before any `RETURN` executes. Worth fixing this properly rather than just noting it as a limitation.

**Why the fail path needs the hash too**

When the check rejects a write, you've just *learned* that this composite key exists — that's valuable information for your cache, not just for the DB. If you don't add it to `local_set` on rejection, the next duplicate attempt for the same key will miss the cache, hit the DB again, and get rejected again — same outcome, but you paid for a DB round-trip you could have skipped. The whole point of the cache is to remember *known* hashes, and "known to be taken" is just as cacheable as "known to be mine."

**Fix: return a structured result instead of raising, so both paths return the hash**

```sql
CREATE TYPE upsert_result AS (
  success       boolean,
  key_hash      bytea,
  existing_id   bigint   -- null on success, populated on conflict
);

CREATE OR REPLACE FUNCTION upsert_entity_signature(
  p_id bigint,
  p_frag_a text,
  p_frag_c text
) RETURNS upsert_result AS $$
DECLARE
  v_composite text;
  v_hash bytea;
  v_existing_id bigint;
  v_frag_b text;
  v_result upsert_result;
BEGIN
  SELECT string_agg(key || '=' || value, '|' ORDER BY key)
    INTO v_frag_b FROM B WHERE id = p_id;

  v_composite := coalesce(p_frag_a,'§') || '#' ||
                 coalesce(v_frag_b,'§') || '#' ||
                 coalesce(p_frag_c,'§');
  v_hash := digest(v_composite, 'sha256');

  PERFORM pg_advisory_xact_lock(hashtext(encode(v_hash, 'hex')));

  SELECT id INTO v_existing_id
    FROM entity_signature
    WHERE key_hash = v_hash AND id != p_id;

  IF v_existing_id IS NOT NULL THEN
    -- no exception — just report the conflict, hash included
    v_result := (false, v_hash, v_existing_id);
    RETURN v_result;
  END IF;

  INSERT INTO entity_signature (id, frag_a, frag_b, frag_c)
    VALUES (p_id, p_frag_a, v_frag_b, p_frag_c)
  ON CONFLICT (id) DO UPDATE
    SET frag_a = EXCLUDED.frag_a, frag_b = EXCLUDED.frag_b, frag_c = EXCLUDED.frag_c;

  v_result := (true, v_hash, null);
  RETURN v_result;
END;
$$ LANGUAGE plpgsql;
```

Application side — one call, both paths handled uniformly:

```python
result = db.execute("SELECT * FROM upsert_entity_signature(%s, %s, %s)", (id, frag_a, frag_c))

local_set.add(result.key_hash)  # cache it either way — success or known-duplicate

if not result.success:
    return reject_to_caller(f"duplicate of entity {result.existing_id}")
```

**Why structured return over exception here**

Exceptions are fine for genuinely exceptional/unexpected errors, but a duplicate-key rejection is an *expected* outcome of a business rule check — treating it as a normal return value rather than an exception makes it natural to extract data (the hash, the conflicting id) from the rejection path, and avoids the app needing exception-handling machinery just to read a value that came back with the failure. It also composes more simply if you ever want to batch multiple checks in one round trip later.

One thing to decide: should `local_set` distinguish "this hash is mine" from "this hash belongs to someone else"? As written above it doesn't — it's just a flat set of known-taken hashes, which is enough to answer "would this be a duplicate," but if you ever need "is this *my* existing key" for update-in-place logic, you'd want a map (`hash -> id`) instead of a set.
