Yes — **very common**, especially in ERP systems.

What you're describing is usually called **duplicate master data**, **duplicate entities**, or **master-data duplication**.

For example, the ERP may contain:

```text
Customer
---------
ID       Name             Tax ID
C001     ABC Technology   12345678
C982     ABC Tech Co.     12345678   <-- same real-world company
```

Even though `C001` and `C982` are technically different records, they represent the **same real-world object**.

### Why this happens so often in ERP

ERP systems usually have many departments and integration points:

```text
Supplier
Customer
Material / Product
Employee
Warehouse
Bank
Company
Business Partner
```

The same real-world entity can enter the system through different processes:

```text
                 ┌── Purchasing
                 │
Supplier ────────┼── Finance
                 │
                 ├── Logistics
                 │
                 └── External API
```

If each process/system creates its own record, duplicates are almost inevitable.

Common causes include:

1. **Different naming**

   ```text
   Apple Inc.
   Apple Incorporated
   APPLE INC.
   Apple Inc.,
   ```

2. **Different identifiers**

   ```text
   Internal supplier code: SUP001
   External supplier code: TW-89321
   Tax ID: 12345678
   ERP ID: 94821
   ```

3. **Multiple source systems**

   ```text
   SAP
   CRM
   WMS
   Supplier Portal
   Legacy ERP
   ```

   Each system may have its own ID.

4. **Manual data entry**

   A user searches for:

   ```text
   "ABC Technology"
   ```

   doesn't find it, and creates another record:

   ```text
   "ABC Technologies Ltd."
   ```

5. **M&A / organizational changes**

   A company changes its legal name:

   ```text
   Old:
   ABC Manufacturing Co., Ltd.

   New:
   ABC Manufacturing Taiwan Co., Ltd.
   ```

   The ERP may treat it as a new entity even though it is effectively the same business relationship.

6. **Integration problems**

   For example:

   ```text
   Supplier Portal
         ↓
   API
         ↓
   ERP
   ```

   If the integration doesn't have a reliable **external ID / natural key / matching rule**, every import can potentially create another record.

---

### The more interesting problem: "Are these actually the same object?"

This is called **entity resolution** or **record linkage**.

For example:

```text
A:
Name = "ABC Technology Co., Ltd."
Tax ID = "12345678"
Address = "Taichung..."

B:
Name = "ABC TECHNOLOGY LTD"
Tax ID = "12345678"
Address = "Taichung..."
```

A human immediately says:

> Same company.

But the database sees:

```text
A.id = 10001
B.id = 18273
```

Therefore, ERP systems often need a **duplicate detection / matching layer**.

A typical architecture is:

```text
                  ┌───────────────┐
                  │ Master Data   │
                  │ Management    │
                  └───────┬───────┘
                          │
                  Entity Resolution
                          │
          ┌───────────────┼───────────────┐
          ↓               ↓               ↓
       Exact match    Fuzzy match     Business rules
          │               │               │
          └───────────────┼───────────────┘
                          ↓
                   Same entity?
                    /          \
                  YES           NO
                   ↓             ↓
              Existing ID    Create new
```

### In serious ERP systems, IDs are usually not enough

A good master-data model normally distinguishes:

```text
Internal ID
     ↓
Canonical Entity
     ↓
External IDs
     ├── SAP ID
     ├── CRM ID
     ├── Supplier Portal ID
     └── Legacy ERP ID
```

For example:

```text
Canonical Supplier
------------------
supplier_id = 10001

External identifiers:
SAP        = 800123
Legacy ERP = SUP-00982
Portal     = TW-ABC-001
Tax ID     = 12345678
```

Then different systems can refer to the **same real-world object** without creating multiple canonical records.

---

### And this becomes especially painful in ERP

Because duplicates aren't merely cosmetic.

Suppose:

```text
Supplier A → 100 purchase orders
Supplier B → 50 purchase orders
```

but A and B are actually the same supplier.

Now you have problems with:

* purchasing history
* payment
* accounts payable
* inventory
* supplier performance
* contracts
* tax reporting
* credit limits
* analytics
* reporting
* forecasting

You can end up with:

```text
ABC Supplier
    ├── PO: $10M
    └── Invoice: $8M

ABC Supplier Ltd
    ├── PO: $3M
    └── Invoice: $2M
```

while management thinks there is only one supplier.

So yes, **duplicate/similar master data is one of the classic and persistent problems in ERP and enterprise systems**.

The broader field is usually called **Master Data Management (MDM)**, with **Entity Resolution / Record Linkage / Deduplication** being the technical mechanisms used to solve it.



Yes. If your scope is specifically **material/product master data**, there are several established solutions. In ERP, this is usually handled as **Material Master Data Management + Material Deduplication / Matching**.

The key is: **don't try to solve duplicates with only a fuzzy name search**. Material identity usually requires a combination of business rules, identifiers, specifications, and similarity matching.

### 1. Define a "material identity"

For example:

```text
Material A
────────────────────────
Description: 3M Double Tape
Brand:       3M
Part No:     9473
Size:        50mm x 10m
Color:       Clear
UOM:         Roll
```

Another record:

```text
Material B
────────────────────────
Description: Double Sided Tape 3M
Brand:       3M
Part No:     9473
Size:        50 mm × 10 m
Color:       Transparent
UOM:         Roll
```

A human can recognize that these are probably the **same material**, even though the descriptions differ.

So I'd model material identity roughly as:

```text
Material
   │
   ├── Manufacturer
   ├── Manufacturer Part Number
   ├── Brand
   ├── Specification
   ├── Dimensions
   ├── Grade
   ├── Material Type
   ├── UOM
   └── Other domain-specific attributes
```

---

## 2. Use a matching hierarchy

A practical implementation is:

```text
                 New Material
                      │
                      ▼
             ┌─────────────────┐
             │ Exact identifiers│
             └────────┬────────┘
                      │
                found?
               /       \
             yes        no
             ↓           ↓
         Duplicate   Attribute match
                         │
                         ▼
                   Similarity score
                         │
              ┌──────────┼──────────┐
              ↓          ↓          ↓
            >95%      70~95%       <70%
              ↓          ↓          ↓
           Duplicate   Review       New
```

For example:

| Match level | Rule                                    | Action                  |
| ----------- | --------------------------------------- | ----------------------- |
| Exact       | Manufacturer + Part No.                 | Automatically duplicate |
| Strong      | Brand + normalized Part No. + key specs | Automatically duplicate |
| High        | Multiple attributes match               | Candidate               |
| Medium      | Description similarity                  | Manual review           |
| Low         | Description only                        | Probably new            |

This is much safer than:

```sql
similarity(material_name) > 0.8
```

---

## 3. Normalize the material description

This is extremely important.

These:

```text
M8 BOLT SS304
M8 Bolt SUS304
M8 SS304 Bolt
M8 BOLT STAINLESS 304
```

should be converted into a normalized representation.

For example:

```text
raw description
      ↓
uppercase
      ↓
remove punctuation
      ↓
normalize units
      ↓
normalize synonyms
      ↓
extract attributes
      ↓
canonical representation
```

Result:

```json
{
  "type": "BOLT",
  "size": "M8",
  "material": "SS304"
}
```

Now matching becomes much easier.

---

# 4. Attribute extraction is probably the most valuable part

For materials, I would strongly recommend **structured attributes** instead of putting everything into `description`.

Instead of:

```text
material
------------------------------
"BLACK RUBBER SEAL 20X30X5 NBR"
```

store:

```text
material_type = SEAL
color         = BLACK
length        = 20
width         = 30
thickness     = 5
material      = NBR
```

Then you can compare:

```text
Material A
type = SEAL
color = BLACK
L = 20
W = 30
T = 5
material = NBR

Material B
type = SEAL
color = BLACK
L = 20
W = 30
T = 5
material = NBR
```

That's a much stronger indication of duplication than text similarity.

---

# 5. Create a material fingerprint

This is something I would seriously consider if you're designing the system yourself.

Create a canonical fingerprint:

```text
fingerprint =
    material_type
  + manufacturer
  + manufacturer_part_no
  + normalized_specifications
```

For example:

```text
BOLT|3M|9473|50MM|10M|CLEAR
```

Then hash it:

```text
SHA-256(...)
```

and store:

```text
material_id
fingerprint
```

Now exact duplicates become extremely cheap to detect.

You can even enforce:

```sql
UNIQUE (fingerprint)
```

for material records where the fingerprint represents a true business identity.

---

# 6. But don't automatically merge everything

This is one of the biggest traps.

For example:

```text
Screw M8 × 20
Screw M8 × 25
```

are obviously similar, but **not duplicates**.

Likewise:

```text
Material A
SS304
M8 × 20

Material B
SS316
M8 × 20
```

Very similar, but different materials.

So you want:

```text
Similarity ≠ Identity
```

This distinction is extremely important in material master management.

# 7. A good production architecture

If I were designing this for an ERP, I'd probably separate it into these components:

```text
                 Material Creation
                        │
                        ▼
               ┌─────────────────┐
               │ Normalization   │
               └────────┬────────┘
                        │
                        ▼
               ┌─────────────────┐
               │ Attribute       │
               │ Extraction      │
               └────────┬────────┘
                        │
                        ▼
               ┌─────────────────┐
               │ Exact Match     │
               │ / Fingerprint   │
               └────────┬────────┘
                        │
                   no exact match
                        │
                        ▼
               ┌─────────────────┐
               │ Candidate Search│
               └────────┬────────┘
                        │
                        ▼
               ┌─────────────────┐
               │ Similarity      │
               │ Scoring         │
               └────────┬────────┘
                        │
              ┌─────────┼─────────┐
              ▼         ▼         ▼
           Duplicate  Review     New
```

For candidate search, you can use:

* PostgreSQL `pg_trgm`
* full-text search
* Elasticsearch/OpenSearch
* vector embeddings
* attribute-based SQL filtering

Given your PostgreSQL background, **PostgreSQL + `pg_trgm` + structured attributes** would actually be a very reasonable first implementation.

## 8. I would use a two-stage matching system

For example:

### Stage 1 — deterministic

```text
Manufacturer Part Number
        ↓
Brand + Part Number
        ↓
Supplier Part Number
        ↓
Normalized specification
```

Fast and highly reliable.

### Stage 2 — probabilistic

For remaining candidates:

```text
description similarity       25%
brand match                  15%
manufacturer match           20%
part number similarity       20%
specification similarity     20%
```

Then:

```text
score >= 0.95
    → likely duplicate

0.75 <= score < 0.95
    → human review

score < 0.75
    → probably new material
```

The exact thresholds should be calibrated against your actual material data.

## 9. Eventually, you can add ML/LLM

For example:

```text
"M8 SS304 HEX BOLT 20MM"

        ↓

LLM / NLP

        ↓

{
  "type": "HEX_BOLT",
  "diameter": 8,
  "length": 20,
  "material": "SS304"
}
```

Then compare structured attributes.

But I **wouldn't start with an LLM**.

A better progression is:

```text
Phase 1
Normalization + exact matching

        ↓

Phase 2
Attribute extraction + rule matching

        ↓

Phase 3
Fuzzy matching / candidate ranking

        ↓

Phase 4
Human review workflow

        ↓

Phase 5
ML / embeddings / LLM
```

This gives you much better explainability, which is particularly important in ERP.

### The most important concept

I'd frame the problem as:

> **"Given two material records, are they representations of the same real-world material?"**

rather than:

> "Are their names similar?"

That distinction leads you toward **Entity Resolution for Material Master Data**, which is a much more robust solution.
